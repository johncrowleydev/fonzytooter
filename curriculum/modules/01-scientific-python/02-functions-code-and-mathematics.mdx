# Functions: Code and Mathematics

You already know how to write functions. In TypeScript, C#, or Python, the basic programming move is familiar: accept some inputs, do some work, and return a result.

```typescript
function fahrenheit(celsius: number): number {
  return (celsius * 9) / 5 + 32
}
```

```python
def fahrenheit(celsius: float) -> float:
    return celsius * 9 / 5 + 32
```

Mathematics uses the same word, **function**, for an idea that is closely related but more precise. If we write `f(c) = 9c / 5 + 32`, we are not describing instructions that a processor executes line by line. We are describing a relationship: for every allowed input `c`, there is a corresponding output.

That distinction is the point of this lesson. You do not need another introduction to programming functions; you need a bridge from the thing you already use every day to the mathematical object that appears everywhere in calculus, linear algebra, statistics, and machine learning.

By the end, expressions like these should feel structurally familiar:

```text
prediction = model(input)
loss = loss_function(prediction, target)
```

```text
f(x) = f₃(f₂(f₁(x)))
```

They are different notations from different worlds, but they are built around the same central idea: **mapping inputs to outputs**.

---

## A mathematical function is a mapping

A common mathematical notation is `f : A → B`, read as “`f` is a function from `A` to `B`.” The essential rule is simple:

> **Every input in `A` is assigned exactly one output in `B`.**

That assignment is what mathematicians mean by a **mapping**. The word sounds abstract, but the idea is not. A mapping just tells you, for each allowed input, which output goes with it.

Suppose:

```text
A = {1, 2, 3, 4}
B = {A, B, C, D, E}
```

and `f` is defined by:

```text
1 → A
2 → C
3 → C
4 → E
```

This is a perfectly valid function. In particular, notice that both `2` and `3` map to `C`. Different inputs are allowed to produce the same output.

What is not allowed is for one input to have two different outputs. This would **not** define a function:

```text
2 → C
2 → D
```

The problem is not that `C` or `D` might have other inputs pointing to them. The problem is that input `2` no longer has one well-defined output.

So keep the direction of the rule straight:

> A function does **not** require every output to have exactly one input. It requires every input to have exactly one output.

That correction matters because “one-to-one” is a real mathematical property, but it is a stronger property than merely being a function.

---

## “One-to-one” is not the definition of a function

Consider the familiar rule:

```text
f(x) = x²
```

Then:

```text
f(2) = 4
f(-2) = 4
```

Two different inputs produce the same output, and `f` is still a function. Every individual input still has exactly one assigned output.

What fails here is a more specific property called **injectivity**, also described as being **one-to-one**. An injective function never sends two different inputs to the same output. In other words, the “one-to-one mapping” you may have had in mind is not the definition of *function*; it is the definition of a particular kind of function.

For now, the distinction to carry forward is:

```text
function:
    every input has exactly one output

injective (one-to-one) function:
    different inputs also have different outputs
```

We will return to injectivity after we make the surrounding vocabulary precise.

---

## Domain, codomain, and image

In the notation `f : A → B`, the set `A` is the **domain**: the collection of inputs the function is allowed to accept. `B` is the **codomain**, the set in which we have declared the outputs to live.

There is one more set worth naming. The **image** of the function is the set of outputs the function actually reaches.

Return to the finite mapping:

```text
f : {1, 2, 3, 4} → {A, B, C, D, E}

1 → A
2 → C
3 → C
4 → E
```

Here:

```text
domain    = {1, 2, 3, 4}
codomain  = {A, B, C, D, E}
image     = {A, C, E}
```

`B` and `D` are in the codomain, but this particular function never produces them. That is the key distinction: the codomain describes the declared destination set; the image describes the outputs that are actually attained.

You will also see the word **range** used for the image, and that is how we will generally use it here. Mathematical terminology is not perfectly uniform across books, so `domain`, `codomain`, and `image` are the least ambiguous terms when the distinction matters.

### A programming analogy

A typed function signature gives a useful approximation of this structure. In TypeScript:

```typescript
function square(x: number): number {
  return x * x
}
```

the parameter type is **domain-like**, while the return type is **codomain-like**. Mathematically, we might describe a corresponding idealized function as:

```text
f : ℝ → ℝ
f(x) = x²
```

The analogy is useful, but it is not exact. A JavaScript `number` is not literally the set of real numbers: floating-point values are finite, `NaN` exists, exceptions can interrupt evaluation, and a program may fail to return at all.

Still, the structural questions are similar: **what kinds of inputs are allowed, and what set of outputs are we claiming the function maps into?**

---

## The codomain is part of the function

It is tempting to think that a function is just its formula. Mathematics is a little more careful.

Take the rule `f(x) = x²`. We could declare:

```text
f : ℝ → ℝ
```

or:

```text
f : ℝ → [0, ∞)
```

The formula is identical, and the actual values produced from real inputs are identical. The declared codomain, however, is different.

That seemingly small change affects properties we care about. The first function does not hit every value in its codomain because it never produces a negative number. The second one does hit every value in its codomain.

So when mathematicians specify a function, the domain and codomain are not decorative metadata around a formula. They are part of the mathematical object, and later they will determine whether a function is onto, whether certain compositions make sense, and whether an inverse can exist between the full sets.

---

## A short historical detour: “function” became more abstract

The modern definition of a function did not appear fully formed. The concept became broader as mathematicians discovered that earlier definitions were too restrictive for the problems they wanted to solve.

Leibniz used the word *function* in the seventeenth century in a geometric context, for quantities associated with curves. In the eighteenth century Euler made functions central to analysis and treated them largely through analytic expressions involving variables and constants, while also moving toward the broader idea of one quantity depending on another.

By the nineteenth century, work around Fourier series and related problems made “a function is a formula” increasingly inadequate. Mathematicians needed to reason about piecewise and irregular assignments that might not be captured by one tidy expression. Dirichlet is strongly associated with this shift toward the modern idea of a function as an assignment of outputs to inputs.

The eventual set-based viewpoint strips away the representation and keeps the structure:

```text
input set → mapping → output set
```

That history is especially useful for a programmer because we have our own tendency to identify a function with its implementation. Mathematics asks you to look through the implementation and focus on the input/output relationship itself.

---

## Functions as transformations

For numerical work, **transformation** is often a useful mental model. Consider:

```python
def center(value: float, mean: float) -> float:
    return value - mean
```

For a fixed `mean`, the function takes a value and transforms it into a centered value. An activation such as ReLU does something similar:

```python
def relu(x: float) -> float:
    return max(0.0, x)
```

Negative inputs are mapped to `0`; positive inputs pass through unchanged.

“Transformation” is an intuition rather than the formal definition, because a function does not have to produce something that looks like a modified version of its input. A function could map a photograph to a label, a string to its length, a database row to a DTO, or a vector to another vector.

So **mapping** is the more general term. **Transformation** is often the more intuitive one, especially once we begin looking at numerical pipelines.

---

## Some functions lose information

Now consider absolute value:

```text
f(x) = |x|
```

Both `3` and `-3` map to `3`. If I show you only the output `3`, you cannot reconstruct which of those two inputs I started with. The function has collapsed two distinguishable inputs into one result.

This gives a more useful intuition for **injectivity** than the vocabulary alone. A function is injective if different inputs always produce different outputs. Equivalently:

```text
if f(a) = f(b), then a = b
```

If two outputs are equal, the inputs must have been equal too. No information about which input you had is lost through collisions.

For example:

```text
f(x) = 2x + 3      injective over ℝ
f(x) = x²          not injective over ℝ
f(x) = |x|         not injective over ℝ
```

A function does not need to be injective. Injectivity simply tells us something extra about the mapping: **distinct inputs stay distinguishable after the transformation.**

---

## Surjective: does the function cover its codomain?

Injectivity asks whether inputs collide. **Surjectivity** asks a different question: does every element of the codomain actually get hit?

A function is **surjective**, or **onto**, when every value in its codomain is produced by at least one input. Using the terminology we already introduced:

```text
surjective exactly when image = codomain
```

Now the two square functions from earlier become useful:

```text
f : ℝ → ℝ
f(x) = x²
```

This `f` is not surjective because no real input produces `-1`, `-10`, or any other negative real number.

But:

```text
g : ℝ → [0, ∞)
g(x) = x²
```

**is** surjective. Every nonnegative real number is the square of at least one real input.

Nothing about the formula changed. Nothing about the domain changed. Only the codomain changed, and that was enough to change the answer to “is this function onto?”

---

## Bijective: no collisions and no missing outputs

A function is **bijective** when it is both injective and surjective. The three terms are easier to remember if you attach them to the problems they rule out:

```text
injective:
    no two inputs collide

surjective:
    no codomain values are missed

bijective:
    neither happens
```

For a bijection, every element of the codomain corresponds to exactly one element of the domain. That makes the mapping reversible in a particularly clean way.

And that is why these terms are worth learning: they give us the language needed to say precisely when an inverse function exists.

---

## Inverse functions undo mappings

Suppose:

```text
f(x) = 2x + 3
```

If `f(x) = 11`, we can recover the input:

```text
11 = 2x + 3
8 = 2x
x = 4
```

The **inverse function** packages that reversal as another mapping:

```text
f⁻¹(y) = (y - 3) / 2
```

So:

```text
f(4) = 11
f⁻¹(11) = 4
```

and more generally:

```text
f⁻¹(f(x)) = x
```

The superscript `-1` does **not** mean reciprocal here. `f⁻¹(x)` is not `1 / f(x)`; it means “apply the inverse mapping of `f`.”

This also corrects another easy misconception: an inverse is not whatever operation merely looks opposite. Changing a sign, reflecting a graph, or replacing `x` with `-x` does not automatically produce an inverse. The inverse has a specific job: **take outputs of the original function and recover their corresponding inputs.**

### Why injectivity matters

Try to reverse `f(x) = x²` over all real numbers. If the output is `9`, the original input could have been `3` or `-3`.

A proposed inverse would therefore receive one input, `9`, and need to return two different outputs. That is not a function. The original square function lost the information needed to tell the two cases apart.

### Why surjectivity matters

Now suppose the square function is declared as:

```text
f : ℝ → ℝ
f(x) = x²
```

What should an inverse `f⁻¹ : ℝ → ℝ` do with `-1`? There is no real input whose square is `-1`, so there is nothing for the inverse to recover.

Put the two conditions together and we get the clean statement:

> A function `f : A → B` has a two-sided inverse `f⁻¹ : B → A` exactly when `f` is bijective.

You will sometimes see a textbook say simply that a function must be “one-to-one” to have an inverse. Usually the inverse is then being defined only on the original function's image, or the codomain is implicitly being identified with the range. With explicit full domain and codomain sets, bijectivity is the clean condition.

---

## Restricting a domain can make a function invertible

The square function becomes reversible if we stop allowing both positive and negative inputs:

```text
f : [0, ∞) → [0, ∞)
f(x) = x²
```

Now each output has exactly one allowed input, so the inverse is:

```text
f⁻¹(x) = √x
```

The formula `x²` did not change. We changed the function by changing its domain and codomain.

That is a pattern worth noticing. Sometimes a rule that is not invertible over a large domain becomes invertible once we restrict the domain to a region where the mapping no longer folds different inputs together.

### Logarithms are another inverse

For a base such as `2`, the exponential function:

```text
f(x) = 2ˣ
```

maps exponents to positive values. Its inverse asks the reverse question: **what exponent would produce this value?**

That inverse is the logarithm:

```text
f⁻¹(x) = log₂(x)
```

So `2³ = 8` and `log₂(8) = 3`.

This is also a good place to pin down one bit of terminology that is easy to mix up:

```text
x²     power function — the variable is the base
2ˣ     exponential function — the variable is the exponent
```

We will study exponentials and logarithms properly later. Here they matter because they give us a concrete example of two important functions that undo one another.

---

## Composition: one function feeds another

Suppose:

```text
f : A → B
g : B → C
```

The output of `f` is suitable as the input of `g`, so we can apply them in sequence:

```text
x → f(x) → g(f(x))
```

Mathematically, that combined mapping is called **composition**:

```text
(g ∘ f)(x) = g(f(x))
```

Read `g ∘ f` as “`g` composed with `f`.” The notation can look backward at first, but evaluation still proceeds from the inside out: first compute `f(x)`, then feed that result into `g`.

In Python, the structure is already familiar:

```python
def double(x: float) -> float:
    return x * 2


def shift(x: float) -> float:
    return x + 3


result = shift(double(4))
# 11
```

The same calculation in mathematical notation is:

```text
f(x) = 2x
g(x) = x + 3

(g ∘ f)(4)
= g(f(4))
= g(8)
= 11
```

This is more than a compact notation trick. Composition lets us build complicated mappings out of simple ones and then reason about the resulting pipeline as another function.

### The pieces have to fit

The domain/codomain language becomes practical here. If `f : A → B` and `g : B → C`, then every output of `f` lands in the kind of set `g` expects as input.

That should feel close to type compatibility in a software pipeline. If one stage produces values the next stage cannot accept, the composition is not well-defined over those inputs.

More generally, `g(f(x))` only makes sense where the outputs of `f` lie inside the domain of `g`. This is one of the first places where domain and codomain stop being vocabulary to memorize and start doing actual work.

---

## Composition is usually order-dependent

Using the functions:

```text
f(x) = 2x
g(x) = x + 3
```

we already found:

```text
(g ∘ f)(4) = 11
```

But reverse the order:

```text
(f ∘ g)(4)
= f(g(4))
= f(7)
= 14
```

So in general:

```text
g ∘ f ≠ f ∘ g
```

Function composition is usually **not commutative**. The order of transformations matters, just as it does in a program.

If the functions are invertible, undoing a composition also reverses the order. If you perform `f` and then `g`, you must undo `g` first and `f` second:

```text
(g ∘ f)⁻¹ = f⁻¹ ∘ g⁻¹
```

The pattern is the same one you already know from procedures. If you `compress → encrypt`, reversing the process means `decrypt → decompress`.

---

## A Python function is not automatically a mathematical function

So far, our Python examples have behaved like mathematical functions:

```python
def square(x: float) -> float:
    return x * x
```

For a given input, the result is fixed, and nothing outside the function is changed.

Python's idea of a “function” is much broader, though. Consider:

```python
current_id = 0


def next_id() -> int:
    global current_id
    current_id += 1
    return current_id
```

The explicit arguments do not determine the output; mutable external state does. Or:

```python
from datetime import datetime


def current_time() -> datetime:
    return datetime.now()
```

The same call at different times produces different values. And a function such as:

```python
def save_user(user) -> None:
    database.insert(user)
```

may matter primarily because it changes the outside world rather than because of anything it returns.

Ordinary programming functions can read or mutate external state, perform I/O, depend on time or randomness, raise exceptions, and communicate through side effects. A mathematical function abstracts away all of that: each allowed input has one fixed associated output.

In programming, a **pure function** is the closest analogue to that mathematical model. Informally, a pure function determines its result from its inputs and has no externally visible side effects:

```python
def normalize(value: float, minimum: float, maximum: float) -> float:
    return (value - minimum) / (maximum - minimum)
```

The distinction matters because mathematical and ML code is often written as though every operation were a clean transformation. The numerical core often can be understood that way, even though the surrounding application still contains files, devices, randomness, logging, networking, and state.

---

## Inputs and outputs do not have to be single numbers

The notation `f(x)` can accidentally make functions look like machines that accept one scalar and return one scalar. Nothing in the definition requires that.

A function can take an ordered pair:

```text
f(x, y) = x + y
```

It can map vectors to vectors:

```text
f : ℝⁿ → ℝᵐ
```

or operate on images, strings, matrices, tensors, or structured records.

From a programming perspective, this should be unsurprising. A function with several named parameters can be viewed mathematically as receiving one structured input. We do not need formal product-set theory yet; the practical point is simply that **“input” and “output” can each be rich mathematical objects**.

That becomes important immediately in machine learning, where the inputs, outputs, and parameters are usually vectors, matrices, tensors, or batches rather than isolated numbers.

---

## Parameterized functions

Now consider:

```text
f(x) = wx + b
```

There are three symbols in the expression, but they need not all play the same role. We might treat `x` as the ordinary input while `w` and `b` are fixed **parameters** that select one member of a family of functions.

For example:

```text
w = 2,  b = 1    gives    f(x) = 2x + 1
w = -3, b = 4    gives    f(x) = -3x + 4
```

Machine learning uses this distinction constantly. A model is often written as:

```text
fθ(x)
```

or:

```text
f(x; θ)
```

where `x` is the data input and `θ` stands for the model parameters. The semicolon in `f(x; θ)` is not a new operation; it is just a visual reminder that the parameters are playing a different conceptual role.

During one forward evaluation, the parameters are treated as fixed and the model maps an input to an output. During training, those parameters are changed. Learning therefore moves us through a family of possible functions.

---

## The machine-learning payoff: models are composed functions

A simple artificial neuron is often written schematically as:

```text
y = σ(wx + b)
```

There are already two transformations inside that one expression. First:

```text
x → wx + b
```

then:

```text
z → σ(z)
```

The full operation is their composition:

```text
x → wx + b → σ(wx + b)
```

For vector inputs, the same idea becomes:

```text
y = σ(Wx + b)
```

where `W` is a matrix and `b` is a vector. We will learn the linear algebra behind that later; the structural idea does not require it yet.

A neural network simply stacks more of these transformations:

```text
x
↓
f₁
↓
f₂
↓
f₃
↓
output
```

or, compactly:

```text
f(x) = f₃(f₂(f₁(x)))
```

The *Deep Learning* text describes feedforward networks in this compositional way: layers are functions composed into a larger mapping, with learned parameters determining which mapping the network implements.

This is not merely a metaphor borrowed from mathematics. **Function composition is part of the actual mathematical structure of the model.**

---

## Loss functions are functions too

Suppose a parameterized model produces a prediction:

```text
ŷ = fθ(x)
```

Training needs some way to compare that prediction with the desired target `y`. A **loss function** maps the prediction and target to a numerical value that represents error:

```text
L(ŷ, y)
```

Substitute the model prediction and the composition becomes visible:

```text
L(fθ(x), y)
```

You can read the pipeline as:

```text
input x
  ↓
model fθ
  ↓
prediction ŷ
  ↓
loss L with target y
  ↓
numerical loss
```

Later, derivatives and gradients will tell us how that final loss changes as the parameters `θ` change. Optimization will use that information to adjust the parameters.

For now, we can understand the structure before we understand the calculus:

> **Machine learning is largely about constructing, composing, and optimizing parameterized functions.**

That sentence is going to keep reappearing in different forms.

## Translate between code and mathematics

Consider:

```python
def affine(x: float, weight: float, bias: float) -> float:
    return weight * x + bias


def relu(x: float) -> float:
    return max(0.0, x)


def neuron(x: float, weight: float, bias: float) -> float:
    return relu(affine(x, weight, bias))
```

A mathematical description is:

```text
a(x; w, b) = wx + b
r(x) = max(0, x)

neuron(x; w, b) = r(a(x; w, b))
```

or, emphasizing composition:

```text
neuron = r ∘ a
```

with `w` and `b` treated as parameters of `a`.

The code and mathematics are not literally identical objects. The Python implementation has floating-point semantics, runtime behavior, names, objects, and possible failure modes. The mathematical expression describes the cleaner mapping that the computation is intended to realize.

Learning to move comfortably between those two views is one of the core skills of scientific programming. You want to be able to look at code and see the mathematics it implements, then look at mathematics and imagine how you would express it clearly in code.

```text

```

### 2. Correct the one-to-one misconception

For `f(x) = x²`, why do `f(2) = 4` and `f(-2) = 4` not stop `f` from being a function? What property does `f` fail instead?

Given:

```text
f : {1, 2, 3, 4} → {A, B, C, D}

```

identify the domain, codomain, and image/range. Is the function injective? Is it surjective?

Compare:

```text

```

with:

```text
g : ℝ → [0, ∞)

```

Which one is surjective, and why? Are either of them injective over the stated domain?

### 5. Can it be inverted?

Why does:

```text
f : ℝ → ℝ

```

have a two-sided inverse, while:

```text
g : ℝ → ℝ
g(x) = x²
```

does not? What domain restriction makes the square function invertible onto `[0, ∞)`?

Given:

```text
f(x) = 2x

```

compute `(g ∘ f)(4)` and `(f ∘ g)(4)`. Are they equal? What does that tell you about function composition in general?

Why is this close to a mathematical function?

```python

    return x * x
```

Why is this not naturally modeled as a mathematical function of its explicit arguments alone?

```python
count = 0


def next_count():
    global count
    count += 1
    return count
```

Explain this structurally before worrying about how it is trained:

```text

```

What is the input to the model? What are the parameters? What becomes the input to the loss function? What kind of output does the loss function produce?

## What you should carry forward

A mathematical function is a mapping from a **domain** to a **codomain** in which every domain input has exactly one output. Different inputs are perfectly allowed to share an output; when they never do, the function has the additional property of being **injective**.

The **image** is the set of outputs the function actually reaches. A function is **surjective** when that image fills the codomain, and **bijective** when it is both injective and surjective. Bijections are exactly the functions that can be reversed by a two-sided inverse between their full domain and codomain.

Composition lets us build larger mappings by feeding one function into another. Programming functions can represent these mappings cleanly, but they are more general than mathematical functions because they can depend on state, perform I/O, mutate data, or have other side effects. Pure computational functions are the closest programming analogue.

Most importantly for what comes next, start seeing ML notation as a system of transformations rather than a wall of symbols:

```text
x → fθ(x) → L(fθ(x), y)
```

A model is a parameterized function. Layers are functions composed with functions. Activations are functions. Losses are functions.

Later, derivatives and gradients will tell us how these functions change. But the object they act on should already feel familiar.

You have been writing functions for years. Now the mathematical version is precise enough to build on.
